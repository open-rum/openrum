OpenRUM runs on infrastructure you control. Choose a deployment path first; the setup and operating responsibilities differ. Both production paths are available in Alpha, without an uptime guarantee.

<Aside type="caution" title="Current support boundary">
  The [local evaluation Compose stack](/docs/self-hosting/compose/) still includes Demo data and
  example credentials; do not expose it to real traffic. The separate production Docker stack
  removes those defaults but remains a single failure domain. The Helm path also needs external data
  services, TLS and an image registry; it is not a one-command cluster installation.
</Aside>

If you want to change OpenRUM's source code rather than evaluate a containerized Instance, follow [Local development](/docs/getting-started/local-development/) instead.

## What you operate

Self-hosting means your team owns the domain and HTTPS, credentials, capacity, service health, upgrades, and recovery. Start with the [architecture](/docs/self-hosting/architecture/) and [external dependencies](/docs/self-hosting/dependencies/), then plan for:

- [Capacity and retention](/docs/self-hosting/capacity/) before accepting real traffic.
- [Backups and a tested restore](/docs/self-hosting/backup-restore/) before the first upgrade.
- [Console authentication](/docs/self-hosting/authentication/) when enabling Google, GitHub, OIDC or LDAP sign-in.
- [Upgrades](/docs/self-hosting/upgrades/), [storage pressure](/docs/self-hosting/storage-pressure/) and [troubleshooting](/docs/self-hosting/troubleshooting/) during operation.
- The [threat model](/docs/self-hosting/security/threat-model/) before exposing Ingest to the internet.

Object storage is optional. Core monitoring runs without a Bucket; Source Map Artifacts require Alibaba OSS or an S3-compatible provider.
