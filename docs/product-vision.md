# Product Vision — OpenRUM

## 1. Vision & Mission

### Vision Statement

让每个拥有高流量前端业务的团队，都能以可预测的成本看清真实用户体验，并在问题影响扩大前完成定位。

### Mission Statement

OpenRUM 通过开源、自部署的前端数据采集与分析平台，把错误、性能、请求和用户行为放进同一条可追溯上下文，帮助团队更快发现问题、解释问题并验证修复。

### Founder's Why

lijie 是一名以 Web 前端为核心能力的程序员，长期面对大型 Web/H5 项目的工程质量问题。公司项目日均 PV 已达千万级，监控不再只是“接一个 SDK、看几张报表”的轻量需求：采样率、保留周期、SDK 开销、查询速度和基础设施费用会直接影响监控是否还能持续使用。

当前使用的阿里云 ARMS 能覆盖部分需求，但实际体验复杂、信息上下文割裂，费用又随流量快速增长。团队被迫在成本和可见性之间做选择：少采数据意味着关键问题可能没有证据，多采数据则意味着预算不可预测。OpenRUM 源于这个真实矛盾，不是为了复制 Sentry 的功能清单，而是要把 Sentry 擅长的错误诊断体验扩展到性能、API 和行为分析，并让高流量团队掌握自己的数据与成本。

创始人的优势在于能同时站在 SDK 使用者、问题排查者和平台建设者的位置判断取舍，并拥有千万级日 PV 的真实验证环境。最大的挑战也很明确：这是一个跨前端 SDK、流式数据、OLAP 查询和 Kubernetes 运维的系统，必须用严格的 MVP 边界换取可交付性。

### Core Values

1. **先解释问题，再展示数据。** 每个页面都应回答“发生了什么、影响谁、下一步看哪里”，而不是堆满图表和指标。无法帮助用户采取行动的指标，不进入默认视图。
2. **成本必须可见且可控。** 采样、保留、事件量和存储占用都要有清晰解释；任何可能显著增加资源消耗的能力，都必须提供预算边界、默认保护和预估影响。
3. **默认保护真实用户。** SDK 以低开销、数据最小化和敏感信息脱敏为默认行为。隐私与安全不是部署后的配置建议，而是事件模型和采集接口的设计约束。
4. **先在真实流量中证明。** 架构判断以公司千万级日 PV 的生产数据为准，不以小规模演示或理论吞吐为准。每个重要版本都要给出性能、稳定性和成本数据。
5. **开放实现，也开放取舍。** 开源不仅是公开代码，还要公开容量模型、已知限制、迁移路径和设计理由，让使用者能独立评估 OpenRUM 是否适合自己。

### Strategic Pillars

1. **高流量下的经济性优先。** 当功能完整度与单位事件成本冲突时，先保证核心诊断链路在可控资源下稳定运行。
2. **统一上下文优先于功能数量。** 错误、页面、请求、性能和版本必须共享一致的事件身份与筛选维度；宁可少做一个模块，也不再制造新的数据孤岛。
3. **五分钟可见价值。** 从创建项目到出现第一批可读指标，用户不应先学习复杂概念或配置大量规则。接入体验是核心产品，而不是文档附属品。
4. **内部替代先于外部增长。** 第一阶段以真实替代 ARMS、降低成本和提升排障效率为成功标准；在此之前，不为社区声量扩张范围。

### Success Looks Like

12 个月后，OpenRUM 已稳定服务公司多个核心 Web/H5 项目，持续处理千万级日 PV 对应的监控事件，关键数据查询满足日常排障需要，综合监控成本较原方案降低至少 50%。前端负责人每周使用质量总览判断风险，业务开发能从问题聚合页直接定位到 Source Map 还原后的代码和关联请求，不再跨三四个系统拼线索。项目在 GitHub 形成可部署版本、完整文档、容量基准和真实案例，出现第一批外部生产用户与贡献者；团队对“每多采一类数据会增加多少成本”有明确答案，而不是靠猜测扩容。

## 2. User Research

### Primary Persona

陈浩，30–38 岁，是一家中大型互联网公司的前端负责人，管理多个 Web/H5 项目和若干业务前端团队。他每天会查看线上质量群、错误趋势、发布记录和业务反馈；遇到事故时，他需要在几分钟内判断影响范围，再把可执行线索交给具体开发者。他技术熟练，能理解 Source Map、采样率、P95 和分布式链路，但没有时间研究复杂查询语法或维护大量仪表盘。

陈浩目前使用 ARMS、日志平台、业务埋点和零散报表。监控费用上涨时，他会降低采样、缩短保留期，或者只给少数核心项目开全量能力，这让他对数据是否完整始终没有信心。他愿意切换到 OpenRUM 的前提不是“功能更多”，而是接入风险可控、核心诊断能力可靠、成本有真实对比，并且现有项目可以渐进迁移而非一次性替换。

### Secondary Personas

**周宁，前端基础设施工程师。** 她负责 SDK、构建插件、接入规范和公共监控配置，是 OpenRUM 的实际部署与推广者。她关心包体积、兼容性、采样策略、数据协议、Source Map 上传和升级成本；如果 SDK 不稳定或文档含糊，她会阻止业务接入。

**王哲，业务前端开发者。** 他通常从告警链接或负责人分派的问题进入平台，希望迅速看到可读堆栈、用户环境、请求失败和前序行为。他不关心底层 ClickHouse 如何工作，但会因为筛选复杂、信息噪声或无法复现而放弃平台。

**林悦，质量或技术管理者。** 她关注版本前后错误率、性能分位数、受影响用户数和修复闭环，用于发布评审与稳定性复盘。她需要可信的趋势和统一口径，但不应拥有查看敏感用户数据的默认权限。

### Jobs To Be Done

**功能性任务：** 当线上指标异常或收到用户投诉时，负责人要快速判断异常是否真实、影响哪些页面与用户、是否与某次发布相关；开发者要从聚合问题进入还原后的源码位置，并查看同一会话中的请求和关键上下文；基础设施工程师要在给定资源预算内控制采样、保留和流量峰值。

**情绪性任务：** 用户希望面对事故时有确定感，知道数据足以支持判断，也知道系统没有因超额或采样而悄悄丢失关键证据。他们希望从“到处找日志”转变为“沿一条证据链排查”。

**社会性任务：** 前端负责人希望向技术管理层证明质量投入有效且成本合理；基础设施工程师希望提供一个团队愿意主动使用、而不是被迫接入的平台；业务开发者希望用清晰证据快速解决问题，而不是在事故群里反复猜测。

### Pain Points

1. **监控成本随流量失控（严重，持续发生）。** 千万级日 PV 下，事件量、保留期和高级能力会显著推高费用。当前应对方式是降低采样或减少覆盖，直接后果是关键时刻证据缺失，且年度预算难预测。
2. **错误、性能、请求和行为上下文割裂（严重，每次复杂排障都会发生）。** 用户需在 ARMS、日志和埋点平台之间手工对齐时间、用户和版本。跨系统拼接既慢又容易得出错误结论，事故恢复时间因此延长。
3. **默认界面信息密度高但行动指引弱（中高频）。** 大量指标和筛选项对平台专家有用，却让普通业务开发者难以找到第一步。结果是团队仍依赖少数熟悉监控平台的人完成排查。
4. **采样与数据丢失不可解释（中高频）。** 用户看到“没有数据”时难以判断是业务正常、SDK 未上报、网关丢弃还是采样导致。该问题会侵蚀对整个平台的信任。
5. **自建系统的运维复杂度（潜在但严重）。** 自部署节省许可证费用，却可能把成本转移到 Kafka、ClickHouse 和 Kubernetes 运维。若没有容量基准、健康指标和升级策略，OpenRUM 会成为新的负担。

### Current Alternatives & Competitive Landscape

**阿里云 ARMS** 的优势是云上集成和较完整的监控产品线，现有团队也已有使用经验；不足是高流量下费用高、体验复杂、数据与成本控制不够透明。切换需要并行接入、口径对齐、容量验证和告警迁移，不能只比较功能表。

**Sentry** 在错误聚合、堆栈还原、发布关联和问题工作流上建立了很高的体验基准，OpenRUM 应学习其“从 issue 到具体事件”的信息结构。它并不天然解决本项目想覆盖的所有 RUM、API、行为与自定义分析场景，且高事件量下的部署与成本仍需团队评估。

**埋点平台、日志平台与自建报表组合** 灵活且可能已经存在，但缺乏统一事件协议、会话上下文和面向前端排障的默认模型。继续使用组合方案无需迁移，却会长期支付协作和排查效率成本。

**什么都不改** 是最强的间接竞争者。只要 ARMS 的费用尚未触发强烈预算压力，团队就会容忍体验问题。OpenRUM 必须用并行运行的实际成本数据和一次真实问题定位案例证明切换价值。

### Key Assumptions to Validate

1. 我们假设自部署后的总拥有成本至少可降低 50%，因为许可证和事件费用将转化为可控基础设施成本。验证方式：选取同一批项目双写 30 天，统一计算计算、存储、网络和人力运维成本。
2. 我们假设团队愿意为数据自主承担一定运维复杂度。验证方式：让非作者的基础设施工程师仅凭文档完成测试环境部署，记录耗时、失败点和后续维护负担。
3. 我们假设“统一上下文”比单独增加更多图表更能缩短排障时间。验证方式：选择 5 个历史事故，让开发者分别使用现有工具和 OpenRUM 完成定位，对比首次有效线索时间。
4. 我们假设一个轻量 SDK 能在默认采样下满足核心项目的性能预算。验证方式：在真实低端设备与弱网环境测量 SDK 的压缩后体积、主线程耗时、内存和请求增量。
5. 我们假设 ClickHouse 架构能以可接受资源处理峰值事件并支持交互查询。验证方式：用生产脱敏流量回放 3 倍预期峰值，测量积压恢复时间、写入失败率和 P95 查询延迟。
6. 我们假设五分钟内出现可读数据足以提高初次接入成功率。验证方式：观察 5–8 名未参与开发的前端工程师完成接入，统计首次事件时间和需要求助的步骤。
7. 我们假设错误、性能和 API 已足以构成第一版价值，Session Replay 可延后。验证方式：记录内部首月问题定位中真正缺少 Replay 才无法解决的案例比例。

### User Journey Map

**认知：** 陈浩在预算复盘或一次难定位事故中意识到现有方案不可持续，从内部技术讨论或一篇千万级 PV 成本案例了解 OpenRUM。他最初持怀疑态度，首先寻找架构、容量和已知限制，而不是营销截图。

**考虑：** 他与周宁评估 SDK 开销、数据归属、部署依赖和迁移成本。清晰的事件量估算器、并行接入方案与 Kubernetes 部署文档降低风险；如果必须先理解大量内部组件，考虑会在此终止。

**首次使用：** 周宁部署最小环境、创建项目、复制 SDK 配置，并在测试页面触发访问、错误和请求。此阶段的主要摩擦是网络策略、跨域、项目密钥和 Source Map 版本不一致，产品必须给出明确诊断。

**魔法时刻：** 数分钟后，质量总览出现真实 PV、错误率、Web Vitals 和慢 API。陈浩点击错误趋势进入聚合问题，看到还原后的源码位置与关联请求，第一次确认这些数据属于同一条上下文。

**习惯形成：** 团队把发布前后对比和高频错误检查纳入日常流程，告警链接直接进入可操作页面。用量页持续解释事件量、采样和保留，避免月末才发现成本异常。

**倡导：** 当 OpenRUM 在一次真实事故中缩短定位时间并在季度内证明成本下降，陈浩会推动更多项目迁移；团队随后以部署经验、容量数据或代码贡献参与开源社区。

## 3. Product Strategy

### Product Principles

1. **默认页必须给出判断，不只是趋势。** 质量总览优先展示错误率、核心 Web Vitals、慢 API 与环比变化，并指出最值得处理的异常。
2. **任何事件都能解释其去向。** SDK、网关、Kafka 和存储层必须暴露接受、采样、丢弃、积压和失败计数，避免“没有数据但不知道为什么”。
3. **高基数字段受治理。** 自定义属性需要长度、数量、保留与索引限制；平台应保护 ClickHouse，而不是允许无限制维度拖垮集群。
4. **渐进替换，不要求一次迁移。** SDK 与部署支持单项目、低采样、并行运行，先证明价值再扩大流量。
5. **调查路径比模块边界重要。** 用户从总览进入问题后，应沿事件、请求、页面和版本继续探索，不应因后端存储不同而中断。

### Market Differentiation

OpenRUM 的差异不是“免费版 Sentry”，而是把高流量前端团队最昂贵的两件事同时解决：数据成本和排障上下文。开源自部署让团队能够按自己的资源、采样和保留策略控制费用；统一事件模型则把错误、性能、API 和用户会话放到同一条调查路径。这个组合对目标用户重要，因为单纯降低存储成本却保留割裂体验，只会得到一个更便宜但仍难用的系统；单纯改善 UI 却不解释单位事件成本，也无法在千万级 PV 下普及。

防御性来自真实规模经验、前端 SDK 质量、可复现的容量模型以及围绕调查工作流形成的数据关联，而不是某个单点图表。每次内部生产验证都会沉淀默认采样、表结构、查询模式和运维边界，这些知识比复制功能更难获得。

### Magic Moment Design

最短路径应只有五步：初始化管理员 → 创建项目 → 复制一段 SDK 配置 → 打开已接入页面并触发一次错误/请求 → 在质量总览看到指标并下钻。默认 SDK 自动采集页面访问、未处理错误、基础 Web Vitals 和 fetch/XHR 摘要，不要求用户先配置埋点模型。

为了让这一时刻可靠发生，项目页必须显示“配置已创建、SDK 已连接、事件已接收、数据已聚合”四段状态；测试事件应绕过普通采样但带明确标记；从接收事件到总览可见的 P95 延迟应小于 60 秒。若 Source Map 尚未上传，错误仍应可见，并明确告诉用户如何从压缩堆栈升级到源码堆栈。

这一魔法时刻可以在 MVP 内实现，但前提是将 Session Replay、漏斗、复杂告警、跨端追踪和高级发布分析移出第一版。否则平台会在用户看到第一张可信总览前耗尽开发周期。

### MVP Definition

**1. JavaScript SDK 与接入诊断。** 自动采集 page view、JavaScript 错误、unhandled rejection、Web Vitals 和 fetch/XHR 摘要；提供批处理、基础采样、敏感字段过滤及连接状态。完成标准是常见现代浏览器中能稳定上报，gzip 后 SDK 核心包目标不超过 30 KB，且示例应用可在五分钟内看到事件。

**2. Go 接入与异步处理链路。** 提供项目密钥校验、限流、负载校验、Kafka 写入和消费者标准化。完成标准是压测下可水平扩展、过载时明确拒绝并记录指标、单条坏事件不会阻塞批次。

**3. 质量总览。** 展示 PV、近似 UV、错误率、LCP/INP/CLS 分位数和慢 API 列表，支持时间、环境、版本和页面筛选。完成标准是新项目收到数据后 60 秒内出现结果，并能从异常卡片进入对应明细。

**4. 错误问题与 Source Map。** 对错误进行稳定指纹聚合，展示趋势、影响用户、环境、版本、原始事件和还原堆栈；Source Map 通过构建脚本上传到 OSS。完成标准是同类错误稳定归组、错误版本能够准确匹配产物、映射失败有可诊断原因。

**5. API 与性能明细。** 提供页面性能和请求列表，包含分位数、状态码、耗时、页面与版本维度；URL 必须标准化以避免路径参数造成基数爆炸。完成标准是用户能从总览定位最慢页面或 API，并查看相应样本事件。

**6. 最小平台治理。** 包含内置账号、项目成员角色、项目级采样配置、保留策略、事件量与丢弃原因统计，以及 Prometheus 健康指标。完成标准是管理员能解释当天数据量和采样效果，并在队列积压或写入失败时收到基础 Webhook 告警。

### Explicitly Out of Scope

**Session Replay。** 它对复现交互问题很有吸引力，但涉及录制协议、隐私遮罩、OSS 分片、播放器和高数据量。待核心事件链路稳定后，在第 3–4 个月用独立试点重新评估。

**漏斗、路径和留存分析。** 这些能力容易把产品拖向通用行为分析平台，也需要更成熟的身份合并与事件治理。先保留自定义事件协议，第 4–6 个月根据内部真实需求决定是否加入。

**完整分布式追踪。** MVP 只保留 `trace_id`、`span_id` 和请求头透传扩展点，不建设后端 tracing 存储与拓扑。待前端问题确实需要跨服务定位且已有后端 OpenTelemetry 基础时再集成。

**复杂发布回归与回滚决策。** MVP 支持 release 字段和基本筛选，不提供自动回归评分、部署集成和回滚建议。真实版本数据积累 4–8 周后再设计。

**企业级 SAML、SCIM、审计导出与多级权限。** MVP 使用本地账号和简单组织角色，可选 OIDC 作为后续扩展。外部企业采用前不投入复杂身份治理。

**AI 根因分析。** 在事件质量、关联准确率和反馈闭环尚未建立时，AI 结论只会放大不确定性；至少在 6 个月后、已有高质量标注案例时考虑。

### Feature Priority (MoSCoW)

**Must Have：** JavaScript SDK；page view 与 UV 会话标识；JavaScript 错误与 Promise 异常；错误指纹聚合；Source Map 上传和解析；Web Vitals；fetch/XHR 监控；自定义事件基础接口；Go 接入网关；Kafka 消费；ClickHouse 查询；PostgreSQL 元数据；质量总览；错误、性能和 API 列表/详情；时间、环境、版本和页面筛选；本地认证；项目与成员；采样、限流、用量和丢弃统计；Prometheus 指标；Kubernetes 部署。

**Should Have：** 基础 Webhook/SMTP 告警；发布前后基本对比；React/Vue 适配器；Redis 缓存与短期去重；OIDC；数据保留配置；SDK 接入诊断；隐私字段规则；CSV 导出。

**Could Have：** 用户行为时间线；Session Replay；漏斗与路径；高级版本回归；更多框架适配器；钉钉、飞书、企业微信与 Alertmanager 通知器；冷数据归档与恢复；跨服务 trace 跳转。

**Won't Have This Time：** 收费订阅、多租户商业计费、移动原生 SDK、后端 APM 全栈替代、完整分布式追踪、SAML/SCIM、AI 根因分析、无代码通用 BI。

### Core User Flows

**流程一：创建项目并看到第一批数据。** 管理员登录并创建组织/项目，选择生产或测试环境，复制 SDK 配置到示例页面，触发访问、请求和测试错误。项目接入页逐步确认连接和事件状态，随后跳转质量总览。成功标准是首次事件在 60 秒内可见，整个流程不超过五分钟且无需修改服务端配置。

**流程二：从错误趋势定位源码。** 前端负责人从总览点击错误率异常，进入按指纹聚合的问题列表，选择影响用户最多的问题，查看版本、浏览器和页面分布，再打开一个具体事件。系统使用 release 与 dist 匹配 OSS 中的 Source Map，还原代码位置并展示同一会话的请求摘要。成功标准是用户在三次点击内从总览到达可分派给开发者的源码线索。

**流程三：定位慢页面或慢 API。** 用户从总览进入性能或 API 模块，按 P75/P95、页面、环境和版本筛选，查看趋势与样本事件，并复制带筛选条件的链接分享。成功标准是能区分普遍退化与少数异常样本，并明确看到标准化 URL、状态码、耗时阶段和关联页面。

### Success Metrics

**首要指标：内部生产流量替代率。** 90 天内，OpenRUM 稳定承载目标项目至少 30% 的前端监控事件为“良好”，达到 60% 且可关闭对应 ARMS 能力为“优秀”。该指标同时约束产品价值、稳定性和迁移信任。

**成本指标：** 在相同项目、采样和保留口径下，总成本降低 35% 为良好，降低 50% 以上为优秀；必须包含计算、存储、网络和估算运维人力。

**魔法时刻指标：** 新项目首次有效数据 P75 小于 5 分钟为良好，小于 3 分钟为优秀；成功完成首次接入的测试用户比例达到 80%/95%。

**诊断效率指标：** 典型错误从告警或总览到获得可分派线索的中位时间低于 10 分钟为良好，低于 5 分钟为优秀；Source Map 成功匹配率达到 95%/99%。

**技术指标：** 接入成功率不低于 99.9%，端到端可见延迟 P95 小于 60 秒，核心查询 P95 小于 2 秒，SDK 对页面主线程新增长任务为零。领先指标包括每日活跃排障用户数、总览到详情下钻率、每周被分享的问题链接数和采样丢弃原因可解释率。

## 4. Brand Strategy

### Positioning Statement

对于需要在高流量 Web/H5 项目中控制监控成本并快速定位线上问题的前端负责人，OpenRUM 是一套开源自部署的前端真实用户监控平台，能够统一分析错误、性能、请求和用户上下文。不同于收费随事件量快速增长或数据彼此割裂的替代方案，OpenRUM 让团队掌握数据、采样、保留和成本，同时保留面向排障的完整证据链。

### Brand Personality

OpenRUM 像团队里那位经验丰富、说话克制的基础设施工程师：先给事实，再指出影响和下一步；不会用红色大字制造恐慌，也不会用“智能洞察”掩盖不确定性。它愿意承认“数据不足”“发生采样”“尚未匹配 Source Map”，并解释为什么。

如果这个品牌是一个人，它会穿简洁耐用的工作服，随身带着清楚的运行手册和容量数据；在事故中冷静，在复盘中坦诚，在发布时不过度承诺。它绝不会隐藏限制、伪造精确度、用模糊术语包装普通图表，或把资源成本留到用户出问题后才说明。

### Voice & Tone Guide

品牌声音始终保持开放、务实、透明和简洁；语气会随场景变化，但不改变事实优先的原则。

|---|---|---|
| 新手接入 | “已创建项目。加入这段 SDK 配置后，打开一次页面即可验证连接。” | “开启全链路智能可观测新时代！” |
| 错误状态 | “过去 5 分钟有 3 个批次写入失败，已自动重试；查看 Kafka 积压。” | “系统异常，请稍后再试。” |

### Messaging Framework

**Tagline：** 看清前端问题，掌控每一份数据成本。

**首页标题：** 为高流量前端团队打造的开源 RUM 平台。

**价值主张一——统一诊断上下文：** 从质量总览进入错误、源码、请求和会话，不再跨多个系统手工拼接证据。

**价值主张二——可预测的规模成本：** 自主设置采样、保留和存储策略，持续看到事件量、丢弃原因和资源影响。

**价值主张三——真实生产规模验证：** 以千万级日 PV 项目作为默认容量目标，公开压测方法、部署档位和已知限制。

**功能描述：** “错误追踪”强调稳定分组、Source Map 与影响范围；“性能监控”强调 Web Vitals 分位数和页面维度；“API 监控”强调标准化端点、失败率和耗时样本；“用量治理”强调采样、保留与成本解释。

**异议处理：** 对“自建是否更贵”，回答应提供双写 TCO 模板和推荐部署档位；对“是否能替代 Sentry/ARMS”，应明确首版边界并建议并行验证；对“数据是否安全”，应解释默认采集范围、脱敏规则和数据留存位置，而不是只说“私有化更安全”。

### Elevator Pitches

**5 秒：** OpenRUM 是面向高流量前端团队的开源自部署 RUM，把错误、性能和请求放在一起，并让监控成本可控。

**30 秒：** 千万级 PV 下，传统前端监控常迫使团队在费用和数据完整性之间做选择，排障时还要跨错误、日志和埋点平台拼上下文。OpenRUM 用轻量 SDK、Go 数据链路和 ClickHouse 统一分析错误、Web Vitals、API 与会话信息，部署在自己的 Kubernetes 和 OSS 上，让团队掌握采样、保留与成本。

**2 分钟：** 前端团队真正缺的往往不是更多监控图表，而是在高流量和真实事故中仍然负担得起、解释得清的证据链。现有云产品接入方便，但费用会随事件量快速增长；为了控制预算，团队降低采样，恰好在最需要证据时看不到完整现场。与此同时，错误、性能、API 和业务行为分布在不同工具里，定位一次问题需要人工对齐用户、时间和版本。

OpenRUM 从这个矛盾出发：用一个开源、自部署的数据平面统一采集前端真实用户数据，用 Sentry 式的问题工作流组织错误，同时把性能和请求带进同一上下文。它不承诺首版替代所有 APM 或行为分析工具，而是先做好最有价值的路径——五分钟接入、看见真实质量、下钻到可执行线索，并持续解释采样和资源成本。

现在具备实现这一产品的条件：ClickHouse、Kafka、Go 和 Kubernetes 已能支撑成熟的流式分析架构，而公司自己的千万级日 PV 项目提供了稀缺的真实验证环境。当前需要的是选择一批核心项目并行接入，用 30 天数据证明三个结果：平台稳定、定位更快、总成本至少降低 50%。

### Competitive Differentiation Narrative

ARMS 等云服务提供完整产品线，但在高事件量下，团队往往无法同时获得充分采样、较长保留和可预测费用；Sentry 定义了优秀的错误诊断体验，却不是所有团队统一处理 RUM、API 与行为数据的唯一答案；日志和埋点组合则把灵活性留给平台团队，把上下文拼接成本留给每个开发者。OpenRUM 的路径是把“数据所有权与成本控制”同“面向问题的统一调查体验”绑定在一起：团队不仅知道发生了什么，也知道这些数据如何被采集、为何被保留、花费多少资源。真正的壁垒将来自千万级 PV 的生产基准、可靠 SDK、稳定事件模型和公开容量经验，而不是比竞争者多几张仪表盘。
