# Product Vision — OpenRUM

## 1. Vision & Mission

### Vision Statement

让每个 Web 产品团队都能自主掌握数据，在同一个开源产品里看懂用户行为并定位影响体验的前端错误。

### Mission Statement

OpenRUM 通过开源、自部署且体验优秀的分析平台，把用户、会话、事件与错误放进同一条上下文，连接 Google Analytics 式行为洞察与 Sentry 式错误诊断。

### Founder's Why

lijie 是一名以 Web 前端为核心能力的程序员，长期面对大型 Web/H5 项目的用户体验与工程质量问题。实际工作中，行为分析常用于发现“用户做了什么、哪里流失”，错误监控则用于回答“为什么失败、如何修复”；两类工具的数据模型和工作流彼此割裂。

OpenRUM 的出发点不是替代某个内部正在使用的供应商，也不是单纯降低监控费用，而是提供一个真正好用的开源、自部署产品：既拥有行为分析的产品视角，又拥有错误追踪的工程深度，并能从群体指标自然下钻到用户、会话和源码线索。

创始人的优势在于能同时站在 SDK 使用者、问题排查者和平台建设者的位置判断取舍，并拥有千万级日 PV 的真实验证环境。最大的挑战也很明确：这是一个跨前端 SDK、流式数据、OLAP 查询和 Kubernetes 运维的系统，必须用严格的 MVP 边界换取可交付性。

### Core Values

1. **先解释问题，再展示数据。** 每个页面都应回答“发生了什么、影响谁、下一步看哪里”，而不是堆满图表和指标。无法帮助用户采取行动的指标，不进入默认视图。
2. **行为与错误必须共享上下文。** 用户、会话、页面、事件、版本和错误采用一致身份与筛选维度；不能让用户在两个产品思维之间手工拼接证据。
3. **默认保护真实用户。** SDK 以低开销、数据最小化和敏感信息脱敏为默认行为。隐私与安全不是部署后的配置建议，而是事件模型和采集接口的设计约束。
4. **先在真实使用中证明。** 产品判断以真实团队是否持续使用行为分析和错误诊断两条路径为准；千万级日 PV 是可靠性验证条件，不是市场定位本身。
5. **开放实现，也开放取舍。** 开源不仅是公开代码，还要公开容量模型、已知限制、迁移路径和设计理由，让使用者能独立评估 OpenRUM 是否适合自己。

### Strategic Pillars

1. **双核心而非监控功能集合。** 行为分析和错误监控拥有同等产品地位，性能、API、告警和用量治理服务于这两条主路径。
2. **统一上下文优先于功能数量。** 行为、错误、页面、请求、用户、会话和版本必须共享一致身份与筛选维度；宁可少做一个模块，也不再制造新的数据孤岛。
3. **五分钟可见价值。** 从创建项目到出现第一批可读指标，用户不应先学习复杂概念或配置大量规则。接入体验是核心产品，而不是文档附属品。
4. **开源产品先于内部替代。** 公司真实流量用于验证可靠性和体验，但文档、部署、默认配置与导航必须从第一天服务外部自部署用户。

### Success Looks Like

12 个月后，OpenRUM 已成为一套可持续自部署的开源产品：产品团队每天用它查看访问、事件、分群、漏斗与路径，工程团队从异常指标或错误聚合直接进入受影响会话和 Source Map 源码。平台稳定处理千万级日 PV，并拥有完整部署文档、容量基准、真实案例、外部生产用户和社区贡献者。用户选择它的首要原因是统一而顺畅的产品体验与数据自主，而不是某一张成本对比表。

## 2. User Research

### Primary Persona

陈浩，30–38 岁，是一家中大型互联网公司的前端负责人，管理多个 Web/H5 项目和若干业务前端团队。他每天会查看线上质量群、错误趋势、发布记录和业务反馈；遇到事故时，他需要在几分钟内判断影响范围，再把可执行线索交给具体开发者。他技术熟练，能理解 Source Map、采样率、P95 和分布式链路，但没有时间研究复杂查询语法或维护大量仪表盘。

陈浩目前需要在行为分析、错误平台、日志和零散报表之间切换。产品指标异常时，他很难把国家、设备、浏览器或渠道分群与具体错误、会话和版本关联起来。他愿意采用 OpenRUM 的前提是接入简单、日常分析足够顺畅、诊断线索可靠，并且数据能够留在自己的基础设施中。

### Secondary Personas

**周宁，前端基础设施工程师。** 她负责 SDK、构建插件、接入规范和公共监控配置，是 OpenRUM 的实际部署与推广者。她关心包体积、兼容性、采样策略、数据协议、Source Map 上传和升级成本；如果 SDK 不稳定或文档含糊，她会阻止业务接入。

**王哲，业务前端开发者。** 他通常从告警链接或负责人分派的问题进入平台，希望迅速看到可读堆栈、用户环境、请求失败和前序行为。他不关心底层 ClickHouse 如何工作，但会因为筛选复杂、信息噪声或无法复现而放弃平台。

**林悦，产品经理或数据分析人员。** 她关注 PV/UV、来源、地区、设备、关键事件、漏斗与留存，希望无需理解监控术语也能探索用户行为，并在指标异常时把调查链接交给工程团队。

### Jobs To Be Done

**功能性任务：** 产品团队要理解用户从哪里来、做了什么、在哪里流失，并按国家、设备、浏览器及自定义属性分群；工程团队要从异常群体或聚合问题进入受影响会话、还原后的源码和关联请求；平台团队要可靠地自部署、升级和治理数据。

**情绪性任务：** 用户希望面对事故时有确定感，知道数据足以支持判断，也知道系统没有因超额或采样而悄悄丢失关键证据。他们希望从“到处找日志”转变为“沿一条证据链排查”。

**社会性任务：** 产品与前端负责人希望用同一份事实讨论体验和质量；基础设施工程师希望提供一个团队愿意主动使用、而不是被迫接入的平台；业务开发者希望用清晰证据快速解决问题，而不是在事故群里反复猜测。

### Pain Points

1. **行为分析与错误诊断上下文割裂（严重，持续发生）。** 用户需在分析、错误和日志平台之间手工对齐时间、用户、会话和版本，既妨碍产品判断，也拖慢工程诊断。
2. **自部署产品可用但不好用（严重，首次试用即发生）。** 接入、导航、筛选和空状态缺少产品化打磨，团队即使重视数据自主，也很难把工具变成日常工作台。
3. **默认界面信息密度高但行动指引弱（中高频）。** 大量指标和筛选项对平台专家有用，却让普通业务开发者难以找到第一步。结果是团队仍依赖少数熟悉监控平台的人完成排查。
4. **采样与数据丢失不可解释（中高频）。** 用户看到“没有数据”时难以判断是业务正常、SDK 未上报、网关丢弃还是采样导致。该问题会侵蚀对整个平台的信任。
5. **自建系统的运维复杂度（潜在但严重）。** 自部署节省许可证费用，却可能把成本转移到 Kafka、ClickHouse 和 Kubernetes 运维。若没有容量基准、健康指标和升级策略，OpenRUM 会成为新的负担。

### Current Alternatives & Competitive Landscape

**Google Analytics 与同类分析产品** 建立了访问、渠道、事件和受众分析的心智，但通常不会把异常行为自然连接到前端错误、源码和请求上下文。

**Sentry** 在错误聚合、堆栈还原、发布关联和问题工作流上建立了很高的体验基准，OpenRUM 应学习其从 issue 到具体事件的清晰结构，同时补上以用户行为和产品指标为入口的探索方式。

**PostHog、Matomo、GlitchTip 等开源产品** 分别覆盖产品分析、流量分析或错误追踪的重要部分。OpenRUM 不靠功能数量取胜，而是把行为洞察与错误诊断做成一条连贯且高完成度的体验。

**埋点平台、日志平台与自建报表组合** 灵活且可能已经存在，但缺乏统一事件协议、会话上下文和面向前端排障的默认模型。继续使用组合方案无需迁移，却会长期支付协作和排查效率成本。

**继续组合多个工具** 是最强的间接竞争者。OpenRUM 必须证明统一上下文能让团队更快理解一次行为异常并到达可执行的工程线索，而不只是省去一次登录。

### Key Assumptions to Validate

1. 我们假设团队确实希望在同一产品中完成行为分析和错误诊断。验证方式：观察真实用户是否在一次调查中使用分群/漏斗和错误/会话两类视图，而不是只使用其中一半。
2. 我们假设开源自部署用户也把接入和 UI 体验视为采用门槛。验证方式：让非作者仅凭文档完成部署与首次分析，记录求助次数、完成时间和次周留存。
3. 我们假设统一上下文能缩短从“指标异常”到“工程线索”的时间。验证方式：选择 5 个真实案例，对比组合工具与 OpenRUM 的首次有效线索时间。
4. 我们假设一个轻量 SDK 能在默认采样下满足核心项目的性能预算。验证方式：在真实低端设备与弱网环境测量 SDK 的压缩后体积、主线程耗时、内存和请求增量。
5. 我们假设 ClickHouse 架构能以可接受资源处理峰值事件并支持交互查询。验证方式：用生产脱敏流量回放 3 倍预期峰值，测量积压恢复时间、写入失败率和 P95 查询延迟。
6. 我们假设五分钟内出现可读数据足以提高初次接入成功率。验证方式：观察 5–8 名未参与开发的前端工程师完成接入，统计首次事件时间和需要求助的步骤。
7. 我们假设 PV/UV、自定义事件、基础分群与漏斗，加上错误聚合、Source Map 和行为时间线，已经能证明双核心价值；路径、留存和 Session Replay 可渐进加入。

### User Journey Map

**认知：** 陈浩在一次转化异常或难定位事故中发现分析与错误工具无法对齐，从 GitHub、前端社区或真实案例了解 OpenRUM。他首先寻找可运行 Demo、部署边界与行为到错误的完整路径。

**考虑：** 他与周宁评估 SDK 开销、数据归属、部署依赖和迁移成本。清晰的事件量估算器、并行接入方案与 Kubernetes 部署文档降低风险；如果必须先理解大量内部组件，考虑会在此终止。

**首次使用：** 周宁部署最小环境、创建项目、复制 SDK 配置，并在测试页面触发访问、错误和请求。此阶段的主要摩擦是网络策略、跨域、项目密钥和 Source Map 版本不一致，产品必须给出明确诊断。

**魔法时刻：** 数分钟后，数据总览出现真实 PV、UV 和关键行为。陈浩按浏览器或国家发现异常分群，打开受影响会话并看到对应错误、还原后的源码与关联请求，第一次感受到分析和诊断属于同一产品。

**习惯形成：** 团队把发布前后对比和高频错误检查纳入日常流程，告警链接直接进入可操作页面。用量页持续解释事件量、采样和保留，避免月末才发现成本异常。

**倡导：** 当 OpenRUM 帮团队从一次行为异常直接定位到错误根因，且日常分析体验足够顺畅，陈浩会推动更多项目接入；团队随后以部署经验、模板或代码贡献参与开源社区。

## 3. Product Strategy

### Product Principles

1. **默认页同时回答产品与工程问题。** 数据总览优先展示访问、关键事件、用户分群与错误影响，并指出值得探索的变化。
2. **任何事件都能解释其去向。** SDK、网关、Kafka 和存储层必须暴露接受、采样、丢弃、积压和失败计数，避免“没有数据但不知道为什么”。
3. **高基数字段受治理。** 自定义属性需要长度、数量、保留与索引限制；平台应保护 ClickHouse，而不是允许无限制维度拖垮集群。
4. **渐进采用，不要求一次迁移。** SDK 与部署支持单项目、低采样和并行运行，先证明一条分析或诊断路径，再扩大事件与团队范围。
5. **调查路径比模块边界重要。** 用户从总览进入问题后，应沿事件、请求、页面和版本继续探索，不应因后端存储不同而中断。

### Market Differentiation

OpenRUM 不是“免费版 Sentry”，也不是另一套只看访问量的分析报表。它以开源自部署和优秀体验为基础，把 Google Analytics 式的访问、事件、分群与漏斗，同 Sentry 式的错误聚合、Source Map 和问题工作流连接起来。差异不在于简单并列两个菜单，而在于用户能从一个异常群体下钻到会话与错误，也能从一个错误反向理解它影响了哪些用户行为。

防御性来自真实规模经验、前端 SDK 质量、可复现的容量模型以及围绕调查工作流形成的数据关联，而不是某个单点图表。每次内部生产验证都会沉淀默认采样、表结构、查询模式和运维边界，这些知识比复制功能更难获得。

### Magic Moment Design

最短路径应只有五步：初始化管理员 → 创建项目 → 复制一段 SDK 配置 → 打开已接入页面并触发一次访问/事件/错误 → 在数据总览看到指标并下钻。默认 SDK 自动采集页面访问、导航、未处理错误、基础 Web Vitals 和 fetch/XHR 摘要，同时提供清晰的自定义事件接口。

为了让这一时刻可靠发生，项目页必须显示“配置已创建、SDK 已连接、事件已接收、数据已聚合”四段状态；测试事件应绕过普通采样但带明确标记；从接收事件到总览可见的 P95 延迟应小于 60 秒。若 Source Map 尚未上传，错误仍应可见，并明确告诉用户如何从压缩堆栈升级到源码堆栈。

这一魔法时刻可以在 MVP 内实现，但前提是只做有界的事件探索、分群和基础漏斗，将留存、完整路径自由探索、Session Replay、跨端追踪和高级发布分析移出第一版。

### MVP Definition

**1. JavaScript SDK 与接入诊断。** 自动采集 page view、JavaScript 错误、unhandled rejection、Web Vitals 和 fetch/XHR 摘要；提供批处理、基础采样、敏感字段过滤及连接状态。完成标准是常见现代浏览器中能稳定上报，gzip 后 SDK 核心包目标不超过 30 KB，且示例应用可在五分钟内看到事件。

**2. Go 接入与异步处理链路。** 提供项目密钥校验、限流、负载校验、Kafka 写入和消费者标准化。完成标准是压测下可水平扩展、过载时明确拒绝并记录指标、单条坏事件不会阻塞批次。

**3. 数据总览与行为分析。** 展示 PV、近似 UV、访问趋势、Top 页面/来源/事件，以及国家、设备、浏览器和自定义属性分群；提供有界事件探索和基础漏斗。完成标准是新项目收到数据后 60 秒内出现结果，并能从异常分群进入会话或错误上下文。

**4. 错误问题与 Source Map。** 对错误进行稳定指纹聚合，展示趋势、影响用户、环境、版本、原始事件和还原堆栈；Source Map 通过构建脚本上传到 OSS。完成标准是同类错误稳定归组、错误版本能够准确匹配产物、映射失败有可诊断原因。

**5. 行为上下文与辅助诊断。** 为用户/会话展示隐私安全的页面、导航、点击、自定义事件、错误和请求时间线；性能与 API 提供支撑异常解释的明细。完成标准是行为指标与错误详情可以双向进入同一上下文。

**6. 最小平台治理。** 包含内置账号、项目成员角色、项目级采样配置、保留策略、事件量与丢弃原因统计，以及 Prometheus 健康指标。完成标准是管理员能解释当天数据量和采样效果，并在队列积压或写入失败时收到基础 Webhook 告警。

### Explicitly Out of Scope

**Session Replay。** 它对复现交互问题很有吸引力，但涉及录制协议、隐私遮罩、OSS 分片、播放器和高数据量。待核心事件链路稳定后，在第 3–4 个月用独立试点重新评估。

**完整路径自由探索和高级留存。** MVP 提供基础漏斗与有界事件探索，但不开放任意高基数路径查询、复杂 cohort 计算或跨设备身份合并；这些能力在事件治理和真实使用稳定后扩展。

**完整分布式追踪。** MVP 只保留 `trace_id`、`span_id` 和请求头透传扩展点，不建设后端 tracing 存储与拓扑。待前端问题确实需要跨服务定位且已有后端 OpenTelemetry 基础时再集成。

**复杂发布回归与回滚决策。** MVP 支持 release 字段和基本筛选，不提供自动回归评分、部署集成和回滚建议。真实版本数据积累 4–8 周后再设计。

**企业级 SAML、SCIM、审计导出与多级权限。** MVP 使用本地账号和简单组织角色，可选 OIDC 作为后续扩展。外部企业采用前不投入复杂身份治理。

**AI 根因分析。** 在事件质量、关联准确率和反馈闭环尚未建立时，AI 结论只会放大不确定性；至少在 6 个月后、已有高质量标注案例时考虑。

### Feature Priority (MoSCoW)

**Must Have：** JavaScript SDK；page view、用户与会话标识；自定义事件和属性；访问/事件趋势；国家、设备、浏览器和自定义属性分群；基础漏斗；行为时间线；JavaScript 错误与 Promise 异常；错误指纹聚合；Source Map 上传和解析；行为与错误双向下钻；Go 接入网关；Kafka 消费；ClickHouse 查询；PostgreSQL 元数据；本地认证；项目与成员；隐私、采样、限流和 Kubernetes 部署。

**Should Have：** Web Vitals 与 API 辅助诊断；基础 Webhook/SMTP 告警；路径与留存基础版；发布前后基本对比；React/Vue 适配器；OIDC；数据保留配置；接入诊断；CSV 导出。

**Could Have：** Session Replay；高级 cohort 与跨设备身份合并；高级版本回归；更多框架适配器；钉钉、飞书、企业微信与 Alertmanager 通知器；冷数据归档与恢复；跨服务 trace 跳转。

**Won't Have This Time：** 收费订阅、多租户商业计费、移动原生 SDK、后端 APM 全栈替代、完整分布式追踪、SAML/SCIM、AI 根因分析、无代码通用 BI。

### Core User Flows

**流程一：创建项目并看到第一批数据。** 管理员登录并创建组织/项目，选择生产或测试环境，复制 SDK 配置到示例页面，触发访问、请求和测试错误。项目接入页逐步确认连接和事件状态，随后跳转质量总览。成功标准是首次事件在 60 秒内可见，整个流程不超过五分钟且无需修改服务端配置。

**流程二：从行为异常定位错误。** 产品负责人按国家、设备、浏览器、来源或自定义属性查看访问与关键事件，建立两到五步漏斗，发现异常分群后打开对应会话时间线；若会话包含错误，可直接进入聚合问题、Source Map 源码与关联请求。成功标准是无需复制用户 ID 或时间范围到另一套工具。

**流程三：从错误趋势定位源码。** 前端负责人从总览点击错误率异常，进入按指纹聚合的问题列表，选择影响用户最多的问题，查看版本、浏览器和页面分布，再打开一个具体事件。系统使用 release 与 dist 匹配 OSS 中的 Source Map，还原代码位置并展示同一会话的行为与请求摘要。成功标准是用户在三次点击内从总览到达可分派给开发者的源码线索。

**流程四：定位慢页面或慢 API。** 用户从总览进入性能或 API 模块，按 P75/P95、页面、环境和版本筛选，查看趋势与样本事件，并复制带筛选条件的链接分享。成功标准是能区分普遍退化与少数异常样本，并明确看到标准化 URL、状态码、耗时阶段和关联页面。

### Success Metrics

**首要指标：双核心激活率。** 90 天内，完成接入的项目中至少 40% 每周同时使用行为分析和错误诊断为“良好”，达到 60% 为“优秀”；只使用单一模块不计为双核心激活。

**分析价值指标：** 至少 5 个真实案例从分群或漏斗异常进入会话/错误线索；关键事件与错误的可关联率达到 90%，核心分析查询 P95 小于 2 秒。

**魔法时刻指标：** 新项目首次有效数据 P75 小于 5 分钟为良好，小于 3 分钟为优秀；成功完成首次接入的测试用户比例达到 80%/95%。

**诊断效率指标：** 典型错误从告警或总览到获得可分派线索的中位时间低于 10 分钟为良好，低于 5 分钟为优秀；Source Map 成功匹配率达到 95%/99%。

**技术指标：** 接入成功率不低于 99.9%，端到端可见延迟 P95 小于 60 秒，核心查询 P95 小于 2 秒，SDK 对页面主线程新增长任务为零。领先指标包括每日活跃排障用户数、总览到详情下钻率、每周被分享的问题链接数和采样丢弃原因可解释率。

## 4. Brand Strategy

### Positioning Statement

对于希望自主掌握数据、又不愿牺牲产品体验的 Web 团队，OpenRUM 是一套开源自部署的用户行为分析与错误监控平台。不同于把 Google Analytics 和 Sentry 分开使用的组合方案，OpenRUM 让访问、事件、分群、漏斗、会话、错误和源码线索共享一条可探索上下文。

### Brand Personality

OpenRUM 像团队里那位经验丰富、说话克制的基础设施工程师：先给事实，再指出影响和下一步；不会用红色大字制造恐慌，也不会用“智能洞察”掩盖不确定性。它愿意承认“数据不足”“发生采样”“尚未匹配 Source Map”，并解释为什么。

如果这个品牌是一个人，它会穿简洁耐用的工作服，随身带着清楚的运行手册和容量数据；在事故中冷静，在复盘中坦诚，在发布时不过度承诺。它绝不会隐藏限制、伪造精确度、用模糊术语包装普通图表，或把资源成本留到用户出问题后才说明。

### Voice & Tone Guide

品牌声音始终保持开放、务实、透明和简洁；语气会随场景变化，但不改变事实优先的原则。

### Messaging Framework

**Tagline：** 看懂用户行为，定位每一个前端错误。

**首页标题：** 开源自部署的用户行为分析与错误监控平台。

**价值主张一——行为与错误连在一起：** 从访问、事件、分群或漏斗进入会话、错误、源码和请求，不再跨多个系统手工拼接证据。

**价值主张二——体验优秀的开源自部署：** 数据留在自己的基础设施中，同时拥有清晰接入、顺畅探索和可分享调查视图。

**价值主张三——真实生产规模验证：** 以千万级日 PV 项目作为默认容量目标，公开压测方法、部署档位和已知限制。

**功能描述：** “行为分析”强调 PV/UV、事件、分群、漏斗和路径；“错误监控”强调稳定分组、Source Map、影响范围与行为上下文；“性能/API”作为解释用户体验异常的辅助证据。

**异议处理：** 对“能否替代 Google Analytics + Sentry”，应明确首版分析与错误能力边界，并用行为到错误的完整 Demo 回答；对“自部署是否复杂”，提供清晰部署档位和升级路径；对“数据是否安全”，解释默认采集范围、脱敏规则和留存位置。

### Elevator Pitches

**5 秒：** OpenRUM 是开源自部署的 Google Analytics + Sentry 替代方向，把用户行为和前端错误放在一起。

**30 秒：** 行为分析告诉你用户做了什么，错误监控告诉你为什么失败，但两者通常互不相通。OpenRUM 用一套轻量 SDK 和统一事件模型连接 PV/UV、自定义事件、分群、漏斗、会话、错误与 Source Map，并部署在你自己的基础设施中。

**2 分钟：** Web 团队通常用分析工具观察访问、事件和转化，再用错误平台处理异常。问题在于两套系统对用户、会话、页面和版本的理解不同：产品团队发现某个浏览器或国家的漏斗下跌后，工程团队仍需重新搜索日志和错误，关键上下文在交接中丢失。

OpenRUM 从这个断点出发：用开源、自部署的数据平面统一采集前端真实用户数据，提供行为分析所需的事件、分群和漏斗，也用 Sentry 式问题工作流组织错误。最有价值的路径是五分钟接入、看见真实行为、发现异常群体，然后直接下钻到会话与可执行源码线索。

现在具备实现这一产品的条件：ClickHouse、Kafka、Go 和 Kubernetes 能支撑成熟的流式分析架构，公司自己的千万级日 PV 项目提供真实验证环境。当前需要用一批核心项目证明三个结果：团队愿意持续使用行为分析、行为与错误能够自然关联、外部用户能独立完成自部署。

### Competitive Differentiation Narrative

Google Analytics 定义了广泛的流量和事件分析心智，Sentry 定义了优秀的错误诊断体验，PostHog、Matomo、GlitchTip 等开源产品也覆盖其中的重要部分。OpenRUM 的路径不是把竞品功能表相加，而是围绕同一用户、会话、页面和版本建立双向调查：从行为异常到错误源码，从错误影响到行为和转化。真正的壁垒来自这种贯通体验、可靠 SDK、稳定事件模型、开源自部署质量与真实规模验证。
